# Output Format

Packem produces two module formats: **ESM** and **CJS**. You do not select them with a
config option — Packem derives them from your `package.json`, along with the entry points
and file names that go with them.

<Callout type="warn">
Browser global formats (IIFE, UMD) are **not supported**. See
[Browser globals](#browser-globals) below for what happens if you try, and what to use
instead.
</Callout>

## How formats are derived

### From export conditions

The `exports` field is the primary signal. Each condition Packem recognises produces the
matching format:

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

→ ESM **and** CJS, written to exactly the paths named above.

An ESM-only package simply omits the `require` condition:

```json
{
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    }
  }
}
```

→ ESM only.

### From `type`, `main` and `module`

For packages without an `exports` field, Packem falls back to the legacy fields, resolving
ambiguous extensions through `type`:

| package.json                              | Output |
| ----------------------------------------- | ------ |
| `"type": "module"`, `"main": "./dist/index.js"`   | ESM    |
| `"type": "commonjs"`, `"main": "./dist/index.js"` | CJS    |
| `"module": "./dist/index.mjs"`            | ESM    |
| `"main": "./dist/index.cjs"`              | CJS    |

Because the format follows the file that will actually be published, the output does not
drift from what consumers resolve. The one way to break that correspondence is to override
`rollup.output.format` yourself — see [Browser globals](#browser-globals).

## File extensions

Extensions come from the paths in `package.json`. Packem warns when an extension
contradicts the format it implies — a `.mjs` file in `main` for a CommonJS package, or a
`.cjs` file in `module`.

| Extension | Format | Notes                                       |
| --------- | ------ | ------------------------------------------- |
| `.mjs`    | ESM    | Always ESM, regardless of `type`            |
| `.cjs`    | CJS    | Always CJS, regardless of `type`            |
| `.js`     | Either | Resolved through `type`                     |

To override the mapping, use [`outputExtensionMap`](/docs/options/output-extension-map).

## Dual package setup

Shipping both formats is the `exports` example above. Point each condition at a distinct
extension so Node never has to guess:

```json
{
  "name": "my-library",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "files": ["dist"]
}
```

Packem's validator checks that every path referenced here is actually produced by the
build, and reports the closest match when one is missing. See
[Package Validation](/docs/examples/configuration/package-validation).

<Callout type="info">
When a CommonJS consumer needs both a default and named exports from the same entry, see
[`cjsInterop`](/docs/options/package-exports).
</Callout>

## Multiple entry points

Additional entries are additional `exports` subpaths — there is no separate entry list:

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./utils": {
      "import": "./dist/utils.mjs",
      "require": "./dist/utils.cjs"
    }
  }
}
```

Both entries are built in both formats. See [Multi Exports](/docs/examples/multi-exports).

## Runtime-specific output

Runtime conditions (`node`, `browser`, `edge-light`, `react-server`) select a build
*environment*, not a module format — each still emits ESM or CJS:

```json
{
  "exports": {
    ".": {
      "browser": "./dist/index.browser.mjs",
      "node": "./dist/index.node.mjs",
      "default": "./dist/index.mjs"
    }
  }
}
```

See [Multi Runtime](/docs/guide/multi-runtime).

## Browser globals \{#browser-globals}

Packem has no IIFE or UMD output. Its `Format` type is `"cjs" | "esm"`, and the module
format of every emitted chunk follows the entry it belongs to.

`rollup.output` is passed through to the underlying bundler, so setting `format` there
does change the shape of the generated code — but **nothing else moves with it**:

```ts
// Does not do what it looks like.
export default defineConfig({
  transformer,
  rollup: { output: { format: 'iife', name: 'MyLib' } },
})
```

The result is IIFE code written to `dist/index.mjs`, the path `package.json#module`
points at. Node reads `.mjs` as ESM, the IIFE exposes no ESM exports, and the package is
broken for every consumer. The override also applies to *both* outputs of a dual build,
so the ESM and CJS files end up byte-identical.

`rollup.output` is a single object, not an array, so a list of per-format outputs is not
expressible either — it is spread into each output Packem generates.

If you need a `<script>`-loadable bundle, build it with a tool that targets that use case
and publish it alongside your Packem output.

## Troubleshooting

**Wrong format at runtime.** `require()` failing with `ERR_REQUIRE_ESM`, or an
`import` resolving to CommonJS, almost always means an extension and a condition
disagree. Check that `require` points at `.cjs` (or a `.js` under
`"type": "commonjs"`), and `import` at `.mjs` (or a `.js` under `"type": "module"`).

**A path in `exports` has no output.** The build only produces what `package.json`
asks for. If a condition names a file Packem never generated, the validator lists it
with the nearest actual output — usually a typo or a stale path from a previous setup.

**Types resolve differently from code.** Run
[`are-the-types-wrong`](/docs/options/declaration-files) to check declarations against
each module resolution mode.
