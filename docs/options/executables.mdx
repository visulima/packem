# Executables

The `exe` option ships your bundle as a single file that runs on machines without Node.js installed — the same job [`pkg`](https://github.com/yao-pkg/pkg) does, built on Node.js' [Single Executable Applications](https://nodejs.org/api/single-executable-applications.html) support instead of a patched runtime.

<Callout type="warn">
  `exe` needs **Node.js >= 25.7.0 on the build machine**, which is where stable `--build-sea` landed. It is not supported under Bun or Deno, and the option is experimental.
</Callout>

```typescript
import { defineConfig } from "@visulima/packem/config";

export default defineConfig({
    exe: true,
    runtime: "node",
});
```

```bash
packem build       # -> build/cli
packem build --exe # or without touching the config
```

Every entry your build produces, except declaration files, becomes an executable in `build/`.

## Cross-compiling

`targets` accepts `pkg`-style strings. Anything you leave out falls back to the build host, and the parts may appear in any order — `linux-node25-x64` and `node25-linux-x64` are the same target.

```typescript
export default defineConfig({
    exe: {
        targets: ["host", "linux-x64", "linux-arm64", "darwin-arm64", "win-x64"],
    },
});
```

| Form                   | Meaning                                                     |
| ---------------------- | ----------------------------------------------------------- |
| `host`                 | The build machine — reuses the running `node`, no download  |
| `linux`                | Platform only; architecture and version default to the host |
| `darwin-arm64`         | Platform and architecture                                   |
| `node25-win-x64`       | Node.js major, resolved to the newest matching release      |
| `node25.7.0-linux-x64` | An exact Node.js release                                    |
| `lts-linux-x64`        | Newest LTS. `latest` and `current` work the same way        |

Platform aliases: `darwin` / `mac` / `macos` / `osx`, `win` / `win32` / `windows`, `linux`.
Architecture aliases: `x64` / `amd64` / `x86_64`, `arm64` / `aarch64`.

Non-host targets download the matching official Node.js binary, verify it against the published `SHASUMS256.txt`, and cache it, so only the first build pays for the download.

## Embedding assets

Files your program reads at runtime, carried inside the binary — `pkg`'s snapshot filesystem.

```typescript
export default defineConfig({
    exe: {
        assets: ["templates/**/*.hbs", "locales/*.json", "!locales/_draft.json"],
    },
});
```

Keys are the paths relative to the project root, so a key is the same string you would have passed to `readFile`. Read them back with the runtime helper:

```typescript
import { getAssetJson, getAssetText } from "@visulima/packem/sea";

const template = await getAssetText("templates/mail.hbs");
const schema = await getAssetJson("schema.json");
```

The helper works in both worlds. Inside the executable it reads the embedded copy; during ordinary `node dist/cli.js` development it falls back to the file on disk, so application code never needs an `if (isSea())` branch.

## Native addons

A project that mixes JavaScript with Rust or C++ — anything built with napi-rs or node-gyp — produces a compiled `.node` addon. Those are embedded and written back out at runtime automatically, with nothing to configure.

```typescript
export default defineConfig({
    exe: { targets: ["host"] }, // .node addons in the output are embedded automatically
});
```

An addon is a shared library, and the dynamic linker only loads one from a real path, so an embedded copy cannot be loaded in place. On first use each addon is written to a directory named after a hash of its contents under the system temporary directory. Set `PACKEM_SEA_NATIVES_DIR` to move that elsewhere — a temporary directory mounted `noexec` will otherwise make the linker refuse the file.

<Callout>
    An executable using native addons needs one writable directory at runtime, so it is not completely self-contained. `pkg` has the same constraint, for the
    same reason.
</Callout>

Addons are built for one platform and architecture, so cross-platform targets are rejected with an error naming them. Build each on a matching machine, such as a CI matrix job. Set `nativeModules: false` to opt out and ship them beside the executable instead.

## Shipping bytecode instead of source

`bytecode` compiles the entry to a V8 code cache ahead of time and embeds only that, so no readable source reaches the binary.

```typescript
export default defineConfig({
    exe: { bytecode: true },
});
```

Two constraints come from V8, and packem fails the build rather than producing something that breaks later:

- **The entry must be CommonJS.** The code cache is reached through `vm.Script`, which compiles classic scripts, not ES modules.
- **The target must be one the build machine can run.** A code cache is only valid for the exact Node.js build that produced it, and producing one means executing that target's binary.

If a code cache is ever rejected at startup, the executable throws a clear error instead of silently running nothing.

<Callout type="warn">
    This raises the cost of reading your code; it is **not** encryption. The source text is gone, but V8 keeps function names and string literals in the cache,
    so identifiers and any embedded URLs remain readable with `strings`. Never ship a secret inside an executable, bytecode or not.
</Callout>

## Compressing the payload

```typescript
export default defineConfig({
    exe: { compress: "brotli" }, // or 'gzip', 'zstd', or true for brotli
});
```

Compresses the embedded assets, the native addons, and the bytecode. Assets are decompressed transparently by `@visulima/packem/sea`, so application code does not change. All three algorithms ship with Node.js.

This shrinks _your payload_, not the whole file: most of an executable's size is the Node.js runtime, which cannot be compressed.

## Output naming

```typescript
export default defineConfig({
    exe: {
        fileName: "[name]-[version]-[platform]-[arch]",
        outDir: "dist/bin",
    },
});
```

Tokens: `[name]`, `[platform]`, `[arch]`, `[node]`, `[version]`. `.exe` is appended for Windows targets.

Without a `fileName`, packem uses `[name]` for a single target and `[name]-[platform]-[arch]` when several are built. If two executables would end up with the same name — a token-free `fileName` shared by several entries, or two targets differing only by Node.js version — the build fails and names both, rather than letting one silently overwrite the other.

## Windows icon and version information

```typescript
export default defineConfig({
    exe: {
        targets: ["win-x64"],
        windows: { icon: "./assets/app.ico", versionInfo: true },
    },
});
```

`versionInfo: true` fills every field from `package.json`; pass an object to override individual fields. Requires the optional `resedit` package.

## macOS code signing

Injecting code invalidates the signature Node.js ships with, and unsigned binaries are killed on sight on Apple silicon, so darwin targets are ad-hoc signed by default.

```typescript
export default defineConfig({
    exe: {
        macos: {
            sign: {
                entitlements: "./build/app.entitlements",
                identity: "Developer ID Application: Acme Inc. (ABCDE12345)",
            },
        },
    },
});
```

## Other options

| Option        | Description                                                  |
| ------------- | ------------------------------------------------------------ |
| `entries`     | Restrict which build entries become executables              |
| `execArgv`    | Node.js flags baked into the executable                      |
| `codeCache`   | Embed a V8 code cache to speed up startup                    |
| `snapshot`    | Build from a V8 startup snapshot                             |
| `checksum`    | Write a `.sha256` or `.sha512` digest beside each executable |
| `nodeVersion` | Node.js version for targets that do not name one             |
| `seaConfig`   | Passthrough for SEA options without a dedicated field        |

## CLI flags

| Flag                      | Option                 |
| ------------------------- | ---------------------- |
| `--exe`                   | enable                 |
| `--exe-target`            | `targets`              |
| `--exe-out-dir`           | `outDir`               |
| `--exe-name`              | `fileName`             |
| `--exe-asset`             | `assets`               |
| `--exe-node-version`      | `nodeVersion`          |
| `--exe-checksum`          | `checksum`             |
| `--exe-code-cache`        | `codeCache`            |
| `--exe-bytecode`          | `bytecode`             |
| `--exe-compress`          | `compress`             |
| `--exe-icon`              | `windows.icon`         |
| `--exe-no-native-modules` | `nativeModules: false` |

```bash
packem build --exe --exe-target host,linux-x64,win-x64 --exe-checksum sha256
```

## Debugging

```bash
NODE_DEBUG=packem:exe packem build --exe
```

Logs every resolved target, download, asset and `sea-config.json`, and keeps the temporary build directory for inspection.

## Differences from `pkg`

|                       | packem `exe`                         | `pkg`                          |
| --------------------- | ------------------------------------ | ------------------------------ |
| Runtime               | Official Node.js builds + SEA        | Patched Node.js builds         |
| Build host            | Node.js >= 25.7.0                    | Node.js >= 16                  |
| Target Node.js        | >= 25.7.0                            | 12 – 24                        |
| Bytecode              | CommonJS entry, host-runnable target | Cross-compiles                 |
| Native addons         | Embedded, extracted at runtime       | Embedded, extracted at runtime |
| musl / Alpine targets | Not supported                        | Supported                      |

The Node.js version floor is the significant one: 25.x is Current, not LTS.
