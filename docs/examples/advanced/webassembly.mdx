# WebAssembly

Packem brings `.wasm` files into the ES module graph. A WebAssembly module's exports
become named ES exports, its imports are resolved as ES imports, and the same file can
also be imported in the *source phase* as a compiled but uninstantiated
`WebAssembly.Module`.

Handling is enabled by default — importing a `.wasm` file needs no configuration.

## Import forms

### ESM integration

Following the [WebAssembly ESM integration proposal](https://github.com/WebAssembly/esm-integration),
each of the module's WebAssembly exports is available as a named import:

```typescript
import { add, memory } from './add.wasm'

export const sum = add(2, 3)
export const pages = memory.buffer.byteLength / 65_536
```

Exports of every kind are bound — functions, memories, tables and globals — so
`memory` above is a real `WebAssembly.Memory`.

If the module declares imports of its own, their module names are treated as ES module
specifiers. Given a module containing `(import "./host.js" "log" ...)`, Packem reads the
binary's import section and emits the corresponding `import * as ... from './host.js'`,
then passes that namespace to the instance:

```javascript title="src/host.js"
export const log = (value) => console.log(value)
```

There is no import object to construct by hand, and `./host.js` is bundled like any
other dependency.

### Source phase

[Source phase imports](https://github.com/tc39/proposal-source-phase-imports) bind the
compiled module rather than an instance, so you can instantiate it more than once — each
time against different imports:

```typescript
import source addModule from './add.wasm'

const instance = new WebAssembly.Instance(addModule, {
  './host.js': { log: console.log },
})
```

<Callout type="warn">
`import source` is a stage 3 proposal, and **TypeScript cannot parse it yet** — nor can
prettier, or the transformers Packem drives (esbuild, swc, oxc, sucrase). Packem rewrites
it before any of them see the file, so the *build* works with any transformer, but `tsc`
will still report a syntax error on a `.ts` file containing it.

Until TypeScript catches up, keep source-phase imports in a `.js` file and describe it
with a hand-written `.d.ts`. The [example](https://github.com/visulima/packem/tree/main/examples/wasm-esm)
is laid out this way.
</Callout>

### Default import

The default export is a init function resolving to a `WebAssembly.Instance`, matching the
shape `@rollup/plugin-wasm` produced. Existing code keeps working:

```typescript
import init from './add.wasm'

const instance = await init()

instance.exports.add(1, 1)
```

Calling it with an import object instantiates a fresh instance; calling it bare returns
the instance the named exports come from.

## Delivery modes

`mode` controls how the module's bytes reach the output.

```typescript title="packem.config.ts"
import { defineConfig } from '@visulima/packem/config'
import transformer from '@visulima/packem/transformer/esbuild'

export default defineConfig({
  transformer,
  rollup: {
    wasm: {
      mode: 'auto',
      maxFileSize: 14_336,
    },
  },
})
```

| Mode         | Behaviour                                                                                       |
| ------------ | ----------------------------------------------------------------------------------------------- |
| `auto`       | Default. Inlines modules up to `maxFileSize`, emits anything larger as an asset.                 |
| `inline`     | Always embeds the bytes as base64, keeping the output a single self-contained file.              |
| `asset`      | Always writes the `.wasm` next to the chunk and loads it at runtime.                             |
| `preserve`   | Leaves the import untouched for a downstream bundler, or a runtime with native `.wasm` support.  |

`preserve` is the mode to reach for when you publish a library that a consuming
application will bundle itself, or when you target a runtime that resolves WebAssembly
imports natively:

```typescript
export default defineConfig({
  transformer,
  rollup: {
    wasm: { mode: 'preserve' },
  },
})
```

The specifier survives into the output exactly as written, so the consumer resolves it
the same way your source did.

## Instantiation

Named exports have to exist by the time the module finishes evaluating, so the wrapper
instantiates the module up front. `instantiation` chooses how:

| Value    | Behaviour                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| `auto`   | Default. Uses top-level `await` only where it is both needed and available.                                         |
| `sync`   | Uses the `WebAssembly.Module` / `WebAssembly.Instance` constructors. Works in CJS output.                            |
| `await`  | Uses top-level `await`. Lifts the browser size limit below, but is ESM-only.                                        |

<Callout type="warn">
A browser main thread refuses to compile more than 4 KB synchronously. Packem therefore
switches to top-level `await` for larger browser builds — but top-level `await` cannot be
represented in CommonJS, so a build that also emits CJS fails with an explanatory error.
Emit ESM only, or use `mode: 'preserve'`, for large browser-targeted modules.
</Callout>

## Options

| Option          | Type                                                | Default                     | Description                                                        |
| --------------- | --------------------------------------------------- | --------------------------- | ------------------------------------------------------------------ |
| `mode`          | `'auto' \| 'inline' \| 'asset' \| 'preserve'`       | `'auto'`                    | How the bytes reach the output.                                    |
| `instantiation` | `'auto' \| 'sync' \| 'await'`                       | `'auto'`                    | How the module is compiled and instantiated.                       |
| `maxFileSize`   | `number`                                            | `14336`                     | Inline threshold for `mode: 'auto'`.                               |
| `fileName`      | `string`                                            | `'[name]-[hash][extname]'`  | Name template for emitted assets.                                  |
| `publicPath`    | `string`                                            | —                           | Prefix for the emitted asset's URL.                                |
| `targetEnv`     | `'node' \| 'browser'`                               | `'node'`                    | Chooses `node:fs` or `fetch` for asset loading.                    |
| `include`       | `FilterPattern`                                     | `/\.wasm$/`                 | Files the plugin handles.                                          |
| `exclude`       | `FilterPattern`                                     | —                           | Files the plugin ignores.                                          |

Set `rollup.wasm` to `false` to turn WebAssembly handling off entirely.

## TypeScript

TypeScript does not know the shape of a `.wasm` import, so declare it:

```typescript title="src/add.wasm.d.ts"
declare module '*.wasm' {
  export const add: (a: number, b: number) => number

  const init: (imports?: WebAssembly.Imports) => Promise<WebAssembly.Instance>

  export default init
}
```

## Migrating from `@rollup/plugin-wasm`

Earlier versions passed `rollup.wasm` straight to `@rollup/plugin-wasm`. Packem now
handles `.wasm` itself, on both the rollup and rolldown backends.

- `maxFileSize`, `fileName`, `publicPath` and `targetEnv` keep their meaning.
- `sync` is replaced by `instantiation`. `instantiation: 'sync'` applies to every module
  rather than to a list of paths.
- The default export is unchanged, so existing `import init from './x.wasm'` code needs
  no edits.
